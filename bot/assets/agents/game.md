## Games

- **Design for play first.** Honor the requested genre and mechanics. In your todo plan, name the player's core action, the obstacle/opponent or puzzle that tests it, and the decisions or skills that make another attempt interesting. Get a complete playable round working early, then improve its feel and presentation.
- **Do not default to a collection loop.** Wandering around a scene to collect scattered coins, orbs, gems, or checkpoints until a counter reaches N is not an adequate substitute for the requested game. Renaming pickups, adding a timer, or decorating the map does not create depth. Only make collection the main activity when the user explicitly requests it; even then, give traversal, route choice, hazards, or opponents meaningful consequences. Pickups can support a stronger core mechanic.
- Build concrete, genre-appropriate challenges: racing needs handling, braking lines and challenging courses/rivals; combat needs readable attacks, aiming/dodging and enemy behavior; platforming needs designed jumps and movement mastery; puzzles need interacting rules and solvable authored challenges. Choose mechanics that fit THIS request rather than reskinning the same collect-and-count template.
- A good first minute teaches the core action through play, tests it, and rewards improvement. Add readable feedback, increasing or varied challenges, a fair failure condition and a quick retry where the genre calls for them. Sandbox requests need satisfying interactive systems and player-driven goals. Prefer a small, complete, replayable experience over a large empty world or feature checklist. Verify that the core loop is enjoyable before spending the remaining budget on scenery, menus, or particles.
- A **playable game**, not an animated scene: objective and controls obvious before or right after play starts; explicit title/play/pause/game-over/replay states; immediate audiovisual feedback for danger, damage, scoring, pickups, combos.
- Frame-rate independent simulation (clamped delta or fixed step). When hidden, reduce rendering/audio work only; **never freeze authoritative multiplayer world time because `document.hidden` or RAF stopped** — follow the multiplayer authority/handoff rules; keyboard controls where sensible plus touch for phones; audio only after a user gesture, with a visible mute; localStorage only for non-sensitive settings/scores/progress; usable resized and on high-DPI.
- Split by system without overengineering: `src/main.ts` (lifecycle → `js/main.js`), `game-state.ts` (state machine/loop), `input.ts`, `audio.ts`, and focused modules (`entities.ts`, `levels.ts`, `ui.ts`, …), styling in `css/game.css`, media in `assets/`. Keep **input, simulation, presentation, and network code in separate modules** with narrow interfaces: input modules read devices and expose intents/actions, simulation computes state without touching DOM/engine scene graphs, presentation renders state, netcode stays behind the net client wrapper. When a module passes a few hundred lines or mixes two of those layers, split it along that seam before extending it — a multi-thousand-line god file that reads input, simulates, renders, and talks to the relay in one loop is a defect, not a deliverable.
- Input state is a read-only source. Compute a fresh movement/output vector each frame and apply deadzone, normalization, clamping, and speed to that copy; never normalize, clamp, scale, or mutate the input-source vector itself, and never reuse it directly as the physics/`publish()` output. Reusing the input-source vector as the computed output leaks simulation corrections back into input and compounds deadzone/scale bugs (stuck movement, accelerating diagonals, drifting touch controls).
- On revisions preserve established controls, mechanics, save data, and levels unless the request changes them.
