## 3D direction

- A curated **3D skill set** is installed under `.opencode/skills/` (`game-3d` plus the `threejs-game-studio` package — a coordinator skill with reference manuals for scenes, rendering, gameplay, VFX, audio, UI, performance, and QA — and the shared game skills). Load the relevant skill before building or substantially revising that subsystem: this file is the rulebook, the skills are the deep how-to. The studio skill's npm/Vite/scaffold instructions do not apply here — the harness owns the build; author under `site/src/` and let it bundle.
- **Use the installed three.js** (`import * as THREE from "three"`) — a real package in the harness-managed `node_modules/` (gitignored, never published; engine code reaches the browser only inside your bundle, tree-shaken to what you import; never run npm or reference `node_modules/` paths from HTML) with **full TypeScript types**, so wrong arguments and misspelled members fail the turn. Never hand-roll raw WebGL and never download a second copy; never introduce a build pipeline of your own.
- Addons (OrbitControls, GLTFLoader, …) fetched with `asset_download` into `site/assets/vendor/addons/` work when they import bare `"three"` (it resolves through the workspace package at build time); adapt `"three/addons/*"` subpath imports.
- **Physics: Rapier is preinstalled** (`import RAPIER from "@dimforge/rapier3d-compat"` — real package with types, WASM inlined so no extra assets; `await RAPIER.init()` once during boot before touching it). Use it for anything needing rigid bodies, stacking, joints, CCD, or robust character collision; do **not** vendor Ammo/Cannon/Jolt, the three `*Physics` CDN helpers, or a hand-rolled solver alongside it. Arcade games whose collision is a few spheres/AABBs may still use plain three math instead — but never both systems for the same objects.
- **Rapier conventions:** three `Object3D`s are visuals only; `RigidBody`/`Collider`s are the simulation. After each fixed physics step, copy body transforms onto their meshes — never also `mesh.position += …` a physics-driven object. Step at a fixed timestep from an accumulator and interpolate renders. Players are a Rapier capsule driven by `World.createCharacterController()` (kinematic), not a dynamic body you fight or a camera pushed by hand. Prefer primitive/convex colliders; triangle meshes only for static level geometry; never dynamic triangle-mesh bodies. Associate meshes and bodies through stable entity IDs so events (collisions, sensors) map back to gameplay cleanly.
- **Rapier entity lifetimes:** destroying an entity and removing it from its tracking collection are one operation — every retire/evict/expiry path removes the entry from the list (`shift`/`splice`) at the same moment it calls `removeRigidBody`/`removeImpulseJoint`/mesh removal. An evicted-but-still-listed entity gets destroyed twice; the second removal panics inside WASM and poisons the world, after which every physics call throws `recursive use of an object detected which would lead to unsafe aliasing in rust`. Never wrap Rapier calls in empty `catch {}` — an exception from a Rapier call means it aborted mid-borrow and the world is likely unusable; make retirement idempotent (a `retired` flag) instead of swallowing. That error's stack names the first victim after the poisoning, not the culprit: hunt the first swallowed exception, not the call in the trace.
- **Static spatial queries: three-mesh-bvh is preinstalled** (`import { computeBoundsTree, MeshBVH } from "three-mesh-bvh"`). Build a BVH once for complex static geometry and use accelerated raycasts for hitscan, line-of-sight, ground, and picking instead of naive `intersectObjects` over large meshes. Dynamic objects belong in Rapier (including its ray/shape casts), not in a rebuilt-per-frame BVH.
- **NPC navigation without a navmesh engine** (none is seeded): waypoint graphs, grid A*, flow fields, or steering with Rapier/BVH raycasts for obstacle sensing cover generated-game levels; do not vendor Recast or hand-build one.
- Split by system: `src/main.ts`, `scene.ts`, `world.ts`, `player.ts`, `input.ts`, `game-state.ts`, `ui.ts`, `audio.ts` — input, simulation, presentation, and netcode stay in separate modules; never let one file grow into a mixed god module.
- Show a loading state for external media/models — never a blank canvas — and a visible fallback panel if WebGL fails to initialize.
- Deliberate camera behavior (no nausea, clipping, disorienting resets); pointer lock only after an explicit gesture with obvious escape; readable orientation via lighting/silhouettes/landmarks/ground cues.
- Keep budgets conservative for ordinary laptops and phones; simple robust collision volumes; reuse vectors/materials/geometries in the render loop instead of allocating per frame; quality/resolution scaling when demanding. Mobile 3D needs intentional touch UI, not WASD assumptions.
