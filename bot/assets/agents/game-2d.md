## 2D direction

- A curated **2D skill set** is installed under `.opencode/skills/` (`game-2d`, `excalibur`, and shared game-feel/camera/input/audio/level/performance/physics/genre skills). Load the relevant skill before building or substantially revising that subsystem.
- **Excalibur 0.32.0 is the 2D game engine**: `import * as ex from "excalibur"` from the harness-managed `node_modules/`. Never run npm, hotlink an engine, vendor another copy, add Vite, or create an import map. The harness bundles and type-checks the real Excalibur package for you. DOM/SVG remains acceptable for card/board/UI-heavy experiences where a game engine is genuinely unnecessary.
- Prefer Excalibur's existing primitives: Engine, Scenes/lifecycle, Actors, graphics/animations, cameras, Loader/ImageSource/Sound, input, actions, particles, TileMap and timers. Use **Active/Fixed collision bodies for moving actors and solid world geometry**, Passive for triggers and PreventCollision for decoration; these are collision behaviors, not separate physics engines.
- For action games, use Excalibur collision for player↔world interaction, but **do not give thousands of swarm enemies/projectiles mutually-colliding physics bodies**. Use lightweight custom movement plus spatial hashing/grid queries for high-count actors and keep Excalibur for rendering/lifecycle.
- Build map art and collision from the **same authored map definition** (tile collision properties or explicit world-space collider data). Never eyeball invisible colliders separately from artwork. During development provide a toggleable physics/collider debug overlay so alignment can be verified.
- Separate shared simulation state from presentation. Excalibur lifecycle hooks / RAF are not a multiplayer authority clock: shared timers use `net.serverNow()` and host migration/resync follows AGENTS.md. Update-hook elapsed time is milliseconds; velocities are pixels per second.
- Start the engine with `suppressPlayButton: true` so its built-in loader does not hide the scene behind a click gate. Unlock audio on the first user gesture; do not require audio permission to draw or play.
- **Render at native display size by default.** Use `DisplayMode.FillContainer` with an explicitly sized container (or `FillScreen` for a full-window game) and keep automatic HiDPI support enabled. The logical resolution must follow the displayed canvas dimensions; do not stretch a fixed low-resolution framebuffer with CSS, `FitScreen`/`FitContainer`, transforms or fractional zoom. Adapt the camera/layout on resize instead. For authored pixel art, use `antialiasing: false`, `snapToPixel: true`, nearest-neighbor sampling and integer sprite/camera zoom; avoid Excalibur's blended `pixelArt: true` preset. Keep DOM text/HUD sharp at normal CSS size.
- Build game feel without losing clarity: tweens, particles, trails, restrained camera shake, squash/stretch, hit flash, sound layering. Pool/cap hot objects; touch controls must not cover the play area; backgrounds, UI, transitions and typography deserve authorship.
- **The photograph is the first frame.** The harness photographs the game as it loads, before anyone plays, so the opening frame must show the playfield as it is meant to be seen — the player in the scene, the world drawn, the camera framed on the action. Never a menu, a loading screen, an empty map or a HUD floating over nothing.
