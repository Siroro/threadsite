# Working on ThreadSite

These instructions apply to this repository. This is the infrastructure that turns Discord threads into persistent static sites and browser games. The generated projects have their own `AGENTS.md` files, assembled from `bot/assets/agents/`; edit those templates when changing the instructions given to generated-project agents.

## Working approach

- Inspect the relevant code, tests, and documentation before changing behavior. Use `rg` for searches.
- Check `git status` before editing. Preserve existing work, including uncommitted changes and deleted files; do not reset, clean, or overwrite unrelated work.
- Carry an authorized fix through implementation and relevant verification. Resolve routine choices without repeatedly asking for confirmation; ask when missing information materially changes the intended behavior.
- Keep changes focused. Follow the existing TypeScript/ESM style, including `.js` extensions in TypeScript imports. Avoid unrelated refactors, dependency upgrades, or formatting churn.
- Give concise progress updates during longer work. Report what changed, what was verified, and any remaining limitation. Distinguish a local fix from a deployed fix.

## Repository map

- `bot/src/commands.ts`: Discord slash-command definitions and registration payload.
- `bot/src/index.ts`: Discord startup, interaction handlers, and service wiring.
- `bot/src/project.ts`: project lifecycle, turn orchestration, validation, and publication.
- `bot/src/opencode.ts`: agent SDK integration, streaming, provider handling, and transport recovery.
- `bot/src/store.ts`: persistent project state and queued/pending turn bookkeeping.
- `bot/src/git.ts`, `forgejo.ts`, `build.ts`, and `publish.ts`: source control, repository access, builds, and static publication.
- `bot/src/progress*.ts` and `project-card.ts`: Discord progress and project cards.
- `bot/src/templates.ts` and `bot/assets/agents/`: generated-project instructions. `bot/assets/skills/` contains project skills.
- `bot/networking/threadsite-net.ts`: browser networking client source. `bot/assets/threadsite-net.js` and `.d.ts` are generated by `build:net`; regenerate them rather than editing them directly.
- `gameserver/`: shared multiplayer relay and protocol/recovery smoke tests.
- `preview/`: in-memory preview compiler, Playwright MCP integration, and browser/Docker checks.
- `opencode/`: agent service configuration, guarded tools, and provider adapter.
- `docker-compose.yml`, `apache/`, and `scripts/`: deployment wiring, proxy examples, and setup helpers.

## Discord commands and error diagnosis

- Place every required slash-command option before every optional option within the same command or subcommand. This applies recursively to nested options.
- `/makegam` must keep required `dimension` and `prompt` before optional `multiplayer` and `name`. Keep multiplayer optional unless the requested behavior changes.
- Keep definitions, interaction handlers, help text, and README examples consistent when changing a command.
- Run `bot/test/commands.test.ts` for command changes. It validates the actual registration payload for required/optional ordering at every level.
- Discord error `50035` with `APPLICATION_COMMAND_OPTIONS_REQUIRED_INVALID` means the registration payload has invalid option ordering. Fix the payload; retries do not repair it.
- A top-level command-registration failure prevents normal bot startup. Global exception logging does not prove that initialization completed or that the bot is healthy.
- Read the full error and nested causes, group repeated occurrences by cause, and fix the source. Do not hide errors or add broad retries just to quiet logs.
- Classify service logs accurately: informational startup lines are not failures, and 404s for nonexistent credential/configuration files can be external probes. Do not create those files or routes to eliminate the 404s.

## Behavior to preserve

- One registered Discord thread owns its project workspace, agent session, and source repository. Preserve durable queue claims and turn identity through failures, stops, resets, and restarts.
- An ambiguous transport failure can leave the agent running. Reconcile persisted history and status before considering another prompt; avoid duplicate turns and do not reset files beneath an unconfirmed running turn.
- Keep build/type/static validation and applicable browser QA before acceptance. Push accepted source before replacing the published site. A failed push must leave the previous live site available.
- Preserve atomic publication and startup recovery of interrupted publishes. Keep old URL redirects and repository/project identity consistent during renames.
- Route every generated-workspace Git operation through `bot/src/git.ts`. Use explicit project repository/worktree paths and trust only that canonical workspace per invocation. Never use `safe.directory=*`, inherit Git routing from the server checkout, or let a missing project `.git` fall back to its parent repository.
- Restart continuation prompts use an inactivity deadline: real agent progress extends it, pending user questions pause it, and status heartbeats alone do not extend it. Preserve abort-on-stall behavior and partial edits.
- Keep generated sites static. Preserve workspace/import boundaries, symlink checks, publication exclusions, and file/byte limits. Changes to this infrastructure may use normal development tools; generated-project tool restrictions are enforced separately in `opencode/`.
- Keep multiplayer client, relay, protocol declarations, and generated instructions consistent. Preserve the selected arena/rooms/singleplayer architecture and existing game tenant identity. Networked games must remain playable solo when the relay is unavailable.
- Preview compilation must match production compilation. Keep bot and preview esbuild versions/settings aligned and retain preview isolation between projects and sessions.
- Keep secrets out of source, test fixtures, generated sites, and user-facing Discord messages. Use placeholders in examples; do not dump `.env`, tokens, or credential files into logs. Keep detailed private diagnostics separate from public status messages.

## Verification

Use Node 24, matching the service images. There is no root npm package: run commands in the appropriate component. Install dependencies with `npm ci` there when needed and preserve lockfiles.

| Change | Checks |
| --- | --- |
| Bot code | From `bot/`: `npm test` and `npm run build` |
| Slash-command definitions | From `bot/`: `node --import tsx --test test/commands.test.ts`, plus bot checks |
| Networking client | From `bot/`: `npm run build:net`; review generated assets and run relevant relay/client checks |
| Relay code | From `gameserver/`: `npm run build`, then the applicable `test:relay`, `test:client`, `test:restart`, `test:durable`, or `test:stall` scripts |
| Preview or provider adapter | From `preview/`: `npm test`; use relevant browser/Docker checks for integration changes |
| Compose configuration | From the repository root: `docker compose config --quiet` |
| Documentation only | Check paths and commands against the repository and run `git diff --check`; no runtime test suite needed |

`test:relay` and `test:client` require a local test relay already listening on port 8090. Restart, durability, and stall tests launch their own relay processes; inspect their port and state-directory requirements before running. Use isolated test state rather than production data.

Preview `test:browser` and `test:warmup` require a built preview Docker image; see README setup. `npm --prefix preview run test:docker` exercises the full isolated Compose integration with a scripted provider and requires Docker.

For a defect, add a focused regression test when it protects meaningful behavior; reproduce the failure before fixing it when practical. Do not add tests that merely duplicate implementation or run service integration checks for unrelated documentation changes. Once relevant checks pass, broaden testing only if an unresolved concern warrants it. Report failures and unavailable prerequisites accurately; never claim a check passed without running it.

## Deployment and maintenance

- Local builds and tests do not update a running deployment. When deployment is in scope, rebuild the affected service and verify its health and logs on the intended host.
- For a bot-only change with its dependencies already running, the root command is `docker compose up -d --build --no-deps bot`. Rebuild other affected services when shared configuration or dependencies change.
- Preserve `data/`, secrets, persistent volumes, and live project workspaces. Do not use volume deletion or destructive resets as routine troubleshooting.
- On Windows, use native PowerShell file operations with literal paths. Resolve and verify targets before recursive deletion or moves; keep them within the intended task directory.
- Update `.env.example` and README when adding configuration or changing user-visible behavior. Keep version files consistent when a release/version change is requested; do not bump versions for every fix automatically.
